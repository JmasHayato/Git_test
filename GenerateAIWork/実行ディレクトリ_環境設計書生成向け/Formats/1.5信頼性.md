# 1.5 信頼性

## 1.5.1 可用性の方針

本システムにおける可用性は以下の方針とする。

|No.|方針|対象ノード|主な対象AWSサービス|説明|
|:-:|---|---|---|---|
|1|Single Instance|XXXXXサーバ|EC2|・冗長化は行わず、1台のノードで稼働する。<br>・ノード利用不可時の自動代替手段を設けず、すべて手動での対応とする。<br>・ノード利用不可時は、該当ノードが担うサービスが停止する。|
|2|Single Instance With AutoReboot/AutoRecover|-|EC2|・冗長化は行わず、1台のノードで稼働する。<br>・EC2 InstanceのOS異常時に、自動的にOS再起動を実行し、回復を図る。<br>・EC2 Instanceのハードウェア異常時に、自動的にInstanceのStop,Startを実行し、稼働するハードウェアを変更する事で回復を図る。<br>・AutoReboot/AutoRecoverによる復旧が完了するまで、該当ノードが担うサービスが停止する。|
|3|Single Isntance with AutoHealing|-|EC2|・冗長化は行わず、1台のノードで稼働する。<br>・1台を希望数としたAutoScalingを構成し、ハードウェア異常時/OS異常時/ELBヘルスチェック失敗時には、特定のAMIからサーバを再作成し、回復を図る。<br>・AutoHealingによる復旧が完了するまで、該当ノードが担うサービスが停止する。|
|4|Multi-AZ Instance|-|EC2|・ELBを併用し、冗長化した構成で複数のノードを稼働する。<br>・ノードの異常発生時には、ELBのヘルスチェックが失敗し、異常が発生しているノードへのトラフィックは停止される。(縮退運転)<br>・異常が発生したノードはすべて手動での復旧対応とする。<br>・その間、残されたノードで縮退運転を行う事により、サービスの継続を図る。|
|5|Multi-AZ Instance with AutoHealing|-|EC2|・ELBを併用し、冗長化した構成で複数のノードを稼働する。<br>・ノードの異常発生時には、ELBのヘルスチェックが失敗し、異常が発生しているノードへのトラフィックは停止される。(縮退運転)<br>・複数台を希望数としたAutoScalingを構成し、ハードウェア異常時/OS異常時/ELBヘルスチェック失敗時には、特定のAMIからサーバを再作成し、回復を図る。<br>・その間、残されたノードで縮退運転を行う事により、サービスの継続を図る。|
|6|Multi-AZ Instance with AutoScaling|-|EC2|ELBを併用し、冗長化した構成で複数のノードを稼働する。<br>・ノードの異常発生時には、ELBのヘルスチェックが失敗し、異常が発生しているノードへのトラフィックは停止される。(縮退運転)<br>・複数台を希望数としたAutoScalingを構成し、ハードウェア異常時/OS異常時/ELBヘルスチェック失敗時には、特定のAMIからサーバを再作成し、回復を図る。<br>・その間、残されたノードで縮退運転を行う事により、サービスの継続を図る。<br>・また、CPU使用率やプロセス数等の数値により、ノード数を増減させ、ノードの処理能力を柔軟に対応させる。|
|7|Multi-AZ Instance with Fail Over|-|RDS/ElastiCache|AWSサービスに付帯されたクラスタリングやレプリケーション等の技術を利用し、冗長化した構成で複数のノードを稼働する。<br>・ノードの異常発生時には、Slave/ReplicaインスタンスをポイントするようにDNS レコードが自動的に変更され、サービスの継続を図る。<br>・フェイルオーバー中は、通常 60 ～ 120 秒の利用不可時間が発生する。<br>・※Java DNS キャッシュメカニズムがどのように機能するかによって、JVM 環境の再設定が必要になる場合があります。|


その他、AWSサービスの可用性については、各サービスのSLAに準拠します。\
